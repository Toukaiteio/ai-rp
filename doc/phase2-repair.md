# Phase 2：自动修复流程

Phase 1 把不合格的回复挡在历史之外，代价是玩家要重新等一次生成。
Phase 2 在拒收之前加一道修复：**只修格式和叙述分工，不重写剧情**，每轮最多一次。

- 代码入口：`lib/engine/repair.ts`（提示词、失败原因翻译、输出清洗，全是纯函数）
- 接线位置：`components/chat/ChatScreen.tsx` 的 `requestRepair` + `runTurn` 收尾
- 测试：`lib/engine/repair.test.ts`（19 条）
- 真机结果：`doc/phase2-repair-check.json`，用 `pnpm repair-check` 重跑

---

## 1. 只修结构，不重写剧情

修复用的系统提示把「不许动」和「允许做」分成两段，逐条列出：

**一个字都不能动**

- 已经发生的事件、谁做了什么
- 角色关系、称呼和态度
- 人物设定、外貌、来历
- 玩家说过的话和玩家做的选择
- 场景地点、时间、天气
- 时间线、事情发生的先后顺序

**允许做的只有六件事**（对应 2.1 的修复目标）

| 允许 | 对应问题码 |
| --- | --- |
| 把不规范的 act 改成 narr，或拆成一个短动作 | `act_overlong`、`act_multi_action`、`act_metaphor`、`act_result` |
| 把混在 act 里的对白拆成 dlg | `act_has_dialogue` |
| 把混在 dlg 里的动作、括号、星号拆出来或删掉 | `dlg_has_action` |
| 删掉替玩家说的话、做的动作、写的心情 | `player_control`、`player_block` |
| 删掉非消息块的标签、函数调用、JSON | `pseudo_tool_text`、`dlg_markup`、`no_blocks` |
| 把 who 改成准确的角色名 | `who_pronoun`、`who_inexact`、`character_drift` |

另外两条约束写死在提示里：**「宁可删掉一句，也不要补一句」**、
**「不要扩写，不要润色，不要调整语气，修复后的篇幅不应明显长于原文」**。

`who` 单独给了硬约束：只有「可以出现在 who 里的名字」名单（角色卡角色 + 已知人名）
里的名字能用，名单之外的一个都不能留——真机跑批里模型第一版修复会把没出场过的
「王掌柜」原样留着，补上这条之后消失了。

## 2. 修复次数：每轮最多一次

```
第一次生成
  ↓ 质量门判 hard
自动修复一次（同一条连接通道，temperature 0.2）
  ↓ 重新过质量门
修好 → 落地（accepted / repaired）
仍不合格 → 拒绝保存，提示重新生成
```

不循环的理由和 2.2 说的一致：模型可能在第二次修复里引入新问题，
而且每多修一次就多等一次生成，玩家的等待比一次格式错误更贵。

代码里这条约束是结构性的——`runTurn` 的收尾只有一处 `if`，没有 `while`：

```ts
if (replyText.trim() && result.status === "rejected" && !controller.signal.aborted) {
  // 修一次，然后无论如何都往下走
}
```

**修完必须重新过一遍质量门。** 修复模型自己也可能写出新问题——
真机 fixture 里就出现过「修完仍然替玩家行动」「修完还是留着一个没出场的人」
「修完把整段写成裸文本」。所以修复结果走的是和第一次生成完全相同的校验路径，
不因为是「修复版」就放行。

## 3. 修复请求的组成

修复请求只有两条消息，**不带聊天历史**：

```
system: 修复器角色 + 不许动清单 + 允许做的六件事 + 块协议
user:   需要修复的问题
        角色名 / 可以出现在 who 里的名字 / 玩家这一轮说的是（截断 400 字）
        原始回复
```

为什么不带历史：历史会让模型把「接着写」当成任务（那就成了重写剧情），
也会把旧错误带回来，还更贵。历史里真正用得上的只有两样——
**玩家这一轮说了什么**（避免再替他说话）和**哪些角色名合法**（避免发明人物），
所以只给这两样。

请求构造是纯函数，可以离线断言「里面没有历史、没有工具标签、长输入被截断」。

## 4. UI 行为

| 情况 | 玩家看到什么 |
| --- | --- |
| 正常（一次过） | 无提示 |
| 软错误自动降级 | 无提示（屏幕上直接是降级后的版本） |
| 自动修复成功 | 无提示，只多等一次「正在修正格式」 |
| 自动修复失败 | 红色提示 + **重新生成** / 取消 |

对应 2.4 的三条要求。两个实现细节：

1. **修复期间先把没通过校验的正文从画面上撤掉。** 让玩家先读到一版错的、
   再眼睁睁看它被换掉，比直接等结果更糟。屏幕上只剩「正在修正格式」，
   修好之后直接出现修好的版本。
2. **技术细节只给开发模式。** 生产环境玩家只看到「这一轮回复没有通过校验，已丢弃，
   不会写进历史」+ 重新生成；开发模式额外显示是「没修成」还是「修了仍不合格」，
   具体原因在 QA 面板里（`report.repairNote`）。

## 5. 真机验证（2026-10-18）

`pnpm repair-check`：6 条故意写坏的候选，走真实的「校验 → 修复 → 再校验」。
模型 `yosei-router / deepseek-v4-flash-200k`。

| 用例 | 修前 | 修后 | 篇幅 | 剧情锚点 |
| --- | --- | --- | --- | --- |
| 旁白里替玩家坐下 | rejected | accepted | 56→42 字（×0.75） | 4/4 |
| who 写成代词 | rejected | accepted | 22→22 字（×1.00） | 3/3 |
| 把记忆调用写成标签 | rejected | accepted | 37→27 字（×0.73） | 3/3 |
| 对白里混进 JSON | rejected | accepted | 30→6 字（×0.20） | 2/2 |
| 整段没有块标记 | rejected | accepted | 36→26 字（×0.72） | 4/4 |
| 一次踩中三条硬错误 | rejected | accepted | 41→21 字（×0.51） | 2/2 |

**修复成功 6/6 · 合格 6/6 · 锚点丢失 0 · 违规内容残留 0 · 平均长度 ×0.65。**

三个结论：

1. **修复确实只删不加。** 平均篇幅降到原来的 65%，没有一条变长——
   这正是「宁可删一句也不补一句」想要的结果。
2. **剧情事实没被改写。** 每条用例都钉了几个和违规部分无关的锚点
   （壁炉、账本、招牌、火钳、雨…），修复后全部还在。
3. **被删掉的都是违规内容。** 替玩家点头挂外套的那两句、没出场过的王掌柜、
   JSON 片段、工具标签，全部消失；而 `who` 不对但内容合理的对白
   （「别滴水」）被保留下来，改挂到角色卡上的角色名下——这正是
   「恢复正确的 who」允许的做法。

## 6. 验收对照

| Phase 2 验收标准 | 落地位置 |
| --- | --- |
| 只修结构，不重写剧情 | `REPAIR_SYSTEM_PROMPT` 逐条列出不许动的东西；真机 6/6 锚点全在、篇幅全部变短 |
| 每轮最多一次 | `runTurn` 收尾只有一处 `if`，没有循环；修复后无论成败都继续往下走 |
| 修复请求不含完整聊天历史 | `buildRepairMessages` 只产出 system + user 两条；`repair.test.ts` 断言 `toHaveLength(2)` |
| 修复请求包含失败原因、原始候选、结构协议、只修不扩写的限制 | 同一次组装的四段内容，测试逐段断言 |
| UI 不打扰用户 | 正常与修复成功都无提示；只有修复失败才出现「重新生成」；技术细节仅开发模式可见 |

## 7. 已知取舍

- **修复会多等一次生成。** 真机上每条 1.2 到 3.2 秒。它只在硬错误时发生，
  而硬错误在 26 组基线里是 0 次，所以日常几乎不会触发。
- **修复可能「修少了」。** 模型倾向于只改最显眼的那一处（比如先把 who 改对，
  下一轮才处理替玩家行动）。所以质量门是最终裁判，修不干净就拒收。
- **修复不重试。** 一次不行就交给玩家重新生成，不自动连修——
  连修会把等待时间叠起来，也可能越修越偏。
- **修复用的是同一个模型。** 没有换更强的模型来修：修复任务比生成简单得多
  （只做删改和对齐），换模型会引入第二套计费和配置，收益不划算。
- **锚点检查是启发式的。** 真机检查用「关键词还在不在」判断剧情有没有被改写，
  抓不到同义改写（比如把「壁炉」换成「炉子」）。要更严得靠人工读 rubric。
