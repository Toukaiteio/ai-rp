# Phase 8：世界书

世界书本来就能用，Phase 8 做的是三件事：**预算花在该花的地方**、
**三本来源分开**、**复杂规则先不引入**。

- 匹配与优先级：`lib/prompt/worldbook.ts`
- 三来源类型：`lib/prompt/types.ts` 的 `LorebookSet`
- 全局书（默认空）：`lib/prompt/global-book.ts`
- 测试：`lib/prompt/worldbook.test.ts`（24 条）
- 真机结果：`doc/phase8-lorebook-check.json`，`pnpm lorebook-check`
- 参考：[SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

---

## 第一阶段：预算和优先级

```
budgetCap: number;   // 单次注入的条目上限，默认 8
tokenCap: number;    // 单次注入的文本预算，默认 2000 token
```

优先级四档，顺序固定：

| 档 | 什么时候 | 标签 |
| --- | --- | --- |
| 1 | `constant: true` | 常驻规则 |
| 2 | 关键词命中当前场景（地点、在场的人、正在发生的事） | 当前场景相关 |
| 3 | 关键词命中玩家这一句 | 玩家刚提到的关键词 |
| 4 | 只命中历史里的旧内容 | 普通背景 |

**关键改动：排序发生在花预算之前。** 以前是「先到先得」——
候选按常驻优先排一遍，然后按顺序塞，塞满就停。那样一条超长的背景条目
只要排得靠前，就能把后面的常驻规则挤掉。现在先分档，再按档位花预算：

```
常驻 → 场景相关 → 玩家刚提到 → 背景
```

预算不够时丢的是背景，不是常驻规则。真机验证里把 `tokenCap` 压到 90，
5 条命中里丢掉 1 条超长背景，3 条常驻规则一条不少。

**场景文字参与扫描。** 这是实现时才发现的：光把场景用于「分档」不够——
只在场景里出现、历史里没提过的条目（角色刚走进的那间屋子）根本进不了候选，
也就谈不上优先级。所以扫描文本 = 最近历史 + 本轮输入 + 当前场景 + 递归内容。

每次匹配都产出一份 `WorldBookReport`：

```ts
{ matched, injected, dropped, byPriority: {...}, bySource: {...}, tokens, tokenCap, budgetCap }
```

它进 `BudgetReport.lorebook`，再进 `GenerationReport.lorebook`，
开发面板里能看到「注入 4/5 · 丢 1 · 87/90 token」和档位、来源分布。

## 第二阶段：角色级与聊天级世界书

```ts
interface LorebookSet {
  global?: WorldBook;   // 这个部署通用
  card?: WorldBook;     // 跟着角色卡走
  chat?: WorldBook;     // 只影响这一场
}
```

分开的理由就是你写的那句：**不会把一整套世界设定强行应用到所有角色和所有小说线**。

| 来源 | 存哪儿 | 什么时候用 |
| --- | --- | --- |
| 全局 | `lib/prompt/global-book.ts` | 整个部署共用的设定 |
| 角色 | 角色卡 `character_book` | 换卡即换 |
| 聊天 | 会话 `chatLorebook` | 临时加的地点、只在这条线上成立的组织 |

三本一起送进匹配器，**同档时按来源具体程度排**：聊天 > 角色 > 全局。
一场对话里临时加的设定，应该压过全局的通用背景。

**全局书默认是空的，而且应该保持为空。** 讲述者的基本规则已经在
`system.ts` 的 `BASE_RULES` 里，再抄一份到世界书只会让同一句话出现两次，
白花 token 还容易改漏一处。部署方确实有全局设定要加时再填。

两本世界书的缓存行为不一样，这是有意的：

- **常驻条目进前缀**（它每轮都在，稳定，吃缓存）；
- **关键词命中的条目进历史之后**，所以换关键词不打掉缓存指纹。

聊天书里如果放常驻条目，它同样进前缀——测试里两条都覆盖了。

## 第三阶段：递归与互斥组（暂不引入）

你写的是「以后再考虑」，所以这一阶段**没有实现**。现在保留的只有已有的
`recursiveScan` / `cascade`（条目 A 触发条目 B 的雏形），其余一律不做：

| 规则 | 现状 |
| --- | --- |
| 条目 A 触发条目 B | 已有 `recursiveScan` / `cascade`，只向前扫描 |
| 同一组只选一条（互斥组） | 未实现 |
| 随机事件 | 未实现。已有 `probability`，是确定性的（seed 决定），不是随机 |
| 冷却时间 | 未实现 |
| 延迟激活 | 未实现 |

不做的理由：这四条都需要「跨轮次记住这条目上次什么时候触发过」，
也就是给世界书加一份运行时状态。那会把世界书从「纯函数匹配」变成有状态的东西，
而现在整条组装链是纯的、可离线测的。真要做，也得先把这份状态放到会话里、
和场景状态一样每轮落盘，不能塞进世界书本身。

## 真机验证（2026-10-18）

`pnpm lorebook-check`：一张卡、三本世界书、连续 3 轮，`deepseek-v4-flash-200k`。

| 轮次 | 注入 | 档位（常驻/场景/玩家/背景） | 来源（全局/角色/聊天） |
| --- | --- | --- | --- |
| 1 | 5/5 | 3 / 0 / 1 / 1 | 1 / 2 / 2 |
| 2 | 6/6 | 3 / 0 / 1 / 2 | 1 / 3 / 2 |
| 3 | 7/7 | 3 / 1 / 1 / 2 | 1 / 3 / 3 |

第 3 轮给了一个场景状态（`location: 柴房门口`），「后院/柴房」那条立刻从背景升到
**当前场景相关**——分档是按真实场景走的，不是摆设。

预算收紧到 90 token 之后：

```
注入 4/5 · 丢 1 · 87 token
档位 常驻3 场景0 玩家2 背景0
常驻规则保住了：是 · 超长背景被丢了：是
```

顺带重跑了 26 组基线（`doc/phase8-worldbook-baseline.json`）：
合格 24 + 可修复 2 + 拒收 0，符合预期 25，平均 120 字，
替玩家行动 0 · 复读 0 · 语言切换 0 · 人物漂移 0。
和 Phase 3/4 的基线在同一水平，说明这一阶段的改动没有把输出质量带偏。

## 验收对照

| Phase 8 要求 | 落地位置 |
| --- | --- |
| 第一阶段：固定预算 `budgetCap` | `WorldBook.budgetCap`（默认 8）+ `tokenCap`（默认 2000），双重封顶 |
| 第一阶段：优先级四档 | `EntryPriority`：常驻 → 场景相关 → 玩家刚提到 → 普通背景 |
| 第一阶段：排序先于花预算 | `matchWorldBook` 先分档排序，再 `capByBudget` |
| 第二阶段：三种来源 | `LorebookSet` 的 `global` / `card` / `chat`，聊天 > 角色 > 全局 |
| 第二阶段：不强行套用到所有角色 | 聊天书挂会话、角色书挂卡、全局书默认空 |
| 第三阶段：暂不引入复杂规则 | 互斥组 / 随机事件 / 冷却 / 延迟激活均未实现，理由见上 |

## 已知取舍

- **预算上限取三本里最宽的那个。** 每本各配一套 `tokenCap` 只会让人困惑，
  真要精细控制时再按来源分别限制。
- **扫描深度和递归开关同理**：取三本里最宽松的（最大 depth、任一开启 recursive）。
- **「当前场景相关」依赖场景状态。** 没接场景状态时这一档永远是 0，
  全部落到玩家提到和背景两档——退化成旧行为，不会出错。
- **全局书是空文件。** 它是一个明确的扩展点，不是忘了填。
- **聊天书目前没有编辑界面。** 数据结构和存储都通了（`ChatSession.chatLorebook`），
  但玩家还不能在界面上加条目；这一层等有实际需求时再接。
- **没有做世界书条目的可视化列表。** 开发面板里只有一行统计
  （注入几条、各档各来源几条），看不到具体是哪几条命中。
