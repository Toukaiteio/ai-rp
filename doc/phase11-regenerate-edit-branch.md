# Phase 11：重新生成、编辑和分支

前十个阶段都在让「一轮回复」变好。Phase 11 处理的是**一轮之后的事**：
写坏了怎么重来、改过历史之后状态怎么办、想走另一条路时原来的故事怎么留住。

- 代码入口：`lib/chat/`（三个模块，全是纯函数）
- 测试：`regenerate.test.ts`（14 条）+ `edit.test.ts`（12 条）+ `branch.test.ts`（23 条）
- 真机结果：`doc/phase11-regenerate-check.json`，`pnpm regenerate-check`

---

## 11.1 重新生成

`planRegenerate` 算「重跑要用什么」，三条硬规则：

| 要求 | 怎么保证 |
| --- | --- |
| 删除上一条错误回复 | 历史截到玩家那一句为止，错误回复不在里面 |
| **不把错误回复放进新请求** | 同上。测试里直接断言新请求的全文不含那版正文 |
| 保留同一个玩家输入 | 从末尾往前找最后一条 user，原样带过去 |
| 可加入临时纠偏指令 | `regenerateNote(previous)` |

**为什么不是简单的 `slice(0, -1)`**：一条回复后面可能还跟着别的消息
（玩家改过历史、或者已经又发了一句）。那种情况下要重跑的不是最后一条。
`planRegenerate` 从末尾往前找真正的那条 assistant，把它和它之后的内容一起丢掉。

纠偏指令长这样：

```
上一版回复未采用，请重写这一轮。
不要复用上一版的动作表达和句式，换一个角度写。
保持单一动作和短对白，不要一次推进太多。
上一版是这样开头的：「她把书往桌上一扣。」，不要再这样写。
```

最后一句只给**开头片段**（24 字），不给全文——给全文模型就顺着抄了。
它只影响这一轮，走 `temporaryNote`，不落盘、不进历史。

### 真机验证（2026-10-18）

`pnpm regenerate-check`：同一段输入跑三遍——原始版、带纠偏重跑、不带纠偏重跑。

| 跑批 | 带纠偏重合度 | 不带纠偏重合度 |
| --- | --- | --- |
| 第一次 | 3% | 9% |
| 第二次 | 2% | 10% |

两次一致：**纠偏把「复用上一版」的比例从约 10% 压到 2-3%**。
错误回复零泄漏，两次都确认过。

**一个诚实的不确定项**：纠偏里写了「保持单一动作和短对白」，
但两次跑批里句长一次变长（68→187 字）一次变短（150→112 字）。
低温下句长本身波动就大，单次跑批不足以判断这一条有没有生效，
所以脚本里把 `shorter` 标成不稳定指标并写了说明。
重合度那一项两次一致，可以当结论。

**为什么用低温测**：温度 0.9 时模型本来就会换写法，
第一次跑批带不带纠偏重合度都是 5%——测不出东西。
低温才是「模型倾向复用上一版」的场合，也就是纠偏真正要解决的场合。

## 11.2 编辑消息

编辑之后要处理的不是「怎么改」，而是**改完之后哪些东西不作数了**。

场景状态、剧情线、摘要、关键事实都是从已落地的正文里推出来的。
玩家把中间某一条改了，那段正文就不作数了，这些状态也就只能算「可能过时」。

```ts
reportStale({ index, role }, throughIndex, totalTurns)
```

`throughIndex` 是这些状态有效到第几条消息为止——**四种状态共用同一个界**。
为什么不给每种各记一个：那需要每轮分别记「场景更新到第几条」「摘要覆盖到第几条」，
而现在的实现里它们本来就是同一批正文推出来的。分开记只会造出一个
看起来更精确、实际对不上的数字。

三种结论：

| action | 什么时候 | 做什么 |
| --- | --- | --- |
| `none` | 改的是状态覆盖范围内最新的一条 | 什么都不用做 |
| `mark` | 改了中间某条 | 标记过时，后面的内容按新写法继续 |
| `resummarize` | 改的位置离末尾 ≥ 6 轮 | 建议重新生成摘要 |

**不自动重算**，这是有意的：重算要么再叫一次模型（花钱、还会漂），
要么本地推（推不出来，因为状态是从正文里读的）。
两样都比「留着旧值但明确标注」更容易把事情搞坏。
界面上只出一条可关闭的提示条。

## 11.3 分支聊天

```ts
interface ChatBranch {
  id: string;
  parentMessageId: string;
  title?: string;
  createdAt: number;
}
```

比建议的形状多两处，都是必需的：

- `BranchTree.messages`：**每条分支自己的消息 id 列表**。
  没有它，「分支」只是个标签，切过去还是同一份内容；
- 分支挂在 `ChatSession` 上（`branchTree` + `activeBranch`），
  不单独开存储层——一条会话就是一棵树，主干加若干支线。

几个要点：

- **主干永远在，且不能删**（`mainBranch()`）；
- **分支视图 = 主干到分叉点 + 分支自己的消息**（`resolveBranch`）。
  分支不是独立的新树，而是「主干 + 从某点起换成另一串」；
- **父消息找不到时退到末尾**，不让分支变成空的（旧存档、删过消息的情况）；
- 上限 12 条分支；标题最多 24 字，没给就用序号。

界面上：每条消息下面一个「分出去」，顶栏在分过支之后出现 `2/3` 这样的切换器。

| Phase 11 要求 | 落地位置 |

| 11.1 不把错误回复放进新请求 | 同上；测试直接断言新请求全文不含它 |
| 11.1 保留同一个玩家输入 | `plan.playerInput` 原样带过去 |

| 11.2 重新解析状态 | 编辑后从那一轮重跑，状态在新的一轮里重新推 |
| 11.2 标记后续状态可能过时 | `reportStale` 返回四种状态 + 一句人话提示 |

## 已知取舍

- **状态过时只提示，不自动重算。** 见 11.2 那一段的理由。玩家自己决定要不要
  重新生成摘要；不理会也不会出错，只是摘要可能和新写法对不上。
- **四种状态共用同一个有效期。** 现在的实现里它们确实来自同一批正文，
  分开记是假精确。等哪天摘要改成异步、滞后几轮，这个界要重新拆。
- **分支之间共享分叉点之前的消息内容。** 切分支只切显示范围；
  分出去的那一刻是复制的。这样主干改动不会影响已有分支，代价是分叉点之前的
  内容存了多份（消息 id 列表，不是正文）。
- **分支没有独立的摘要和状态。** 场景状态和剧情线目前仍是会话级的，
  切分支不会切换它们。真要做到「每条支线各有一套状态」，
  得把 `sceneState` / `storyThreads` 也按分支存——那是下一步。
- **重新生成的句长效果没测准。** 见上面那个不确定项。
