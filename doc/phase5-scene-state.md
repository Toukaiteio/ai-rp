# Phase 5：场景状态系统

前四个阶段解决「这一轮写得好不好」。Phase 5 开始解决「第 30 轮还知不知道自己在哪儿」：
给每一轮一个明确的「现在是什么情况」，并且**只记变化、不让猜测变成设定**。

- 代码入口：`lib/scene/`（类型、更新规则、提示词格式，全是纯函数）
- 提取来源：导演阶段顺带输出（`lib/prompt/turn-plan.ts` 的 `statePatch`）
- 组装位置：回合层里的「当前场景」（`lib/prompt/system.ts`）
- 存储：会话（`ChatSession.sceneState`），重置会话即回到起点
- 测试：`lib/scene/state.test.ts`（27 条）
- 真机结果：`doc/phase5-state-check.json`，用 `pnpm state-check` 重跑

---

## 1. 场景状态模型

字段照 5.1 的约定，另加两张表：

```ts
interface SceneState {
  location: string;
  time: string;
  weather?: string;
  presentCharacters: string[];
  currentAction: string;
  emotionalTone?: string;
  unresolvedThreads: string[];
  lastUpdatedAt: number;
  // 每个字段是确认的事实、推断还是不确定（5.3）
  status: Record<SceneFieldKey, StateFactStatus>;
  // 每个字段是第几轮定下来的，用来判断它有多旧
  updatedTurn: Record<SceneFieldKey, number>;
  // 被挡下来的改动，等人确认
  pending?: StateConflict[];
}
```

**和记忆的分工**：记忆（journal / facts）记「已经发生过的事」，长线、跨场景；
场景状态记「此刻」，每轮都可能变，变了就覆盖。所以它不写进前缀（会打掉缓存），
而是拼进回合层。

两张表而不是把每个字段包成 `{ value, status }`：提示词拼装和存储是最常读写的地方，
保持扁平更省事。

## 2. 更新方式：导演顺便给，只保存变化项

```
正文生成
  ↓
状态提取（导演阶段顺带输出 statePatch）
  ↓
比较旧状态（applyScenePatch）
  ↓
只保存变化项
```

第一版按建议走「导演阶段顺便输出」：导演本来就已经读过完整聊天记录，
多输出一个字段几乎不花钱，不用再加一次模型调用。

```
{ "beats": [...], "mode": "dialogue",
  "statePatch": { "location": "图书馆", "currentAction": "她在翻书",
                  "status": { "location": "confirmed", "currentAction": "inferred" } } }
```

四条规则：

1. **只记变化**：值没变的字段不进 `changes`，也不刷新 `updatedTurn`。
   这样「这个字段是第几轮定下来的」才真的是它最后一次变化的轮次。
2. **空值不清空**：patch 里没给的字段一律保持原样。
3. **瞬时字段每轮都更新**：`currentAction`、`emotionalTone` 描述的是此刻这一下，
   不受覆盖保护（下面 5.3 会讲为什么）。
4. **落地时机**：状态在这一轮**生成完之后**才应用。导演给的是「这一轮会变成什么」，
   提前写进状态会让模型把还没发生的事当成已确认的事实。

服务端路径下前端看不到导演计划，所以 `statePatch` 随 SSE 的 `meta` 帧回传
（`lib/wire.ts`），前端拿到之后同样在这一轮落地后再应用。

## 3. 状态不覆盖事实

```ts
type StateFactStatus = "confirmed" | "inferred" | "uncertain";
```

| 可信度 | 什么时候用 | 提示词里怎么说 |
| --- | --- | --- |
| `confirmed` | 正文里明确写到的事：人在哪儿、什么时候、谁在场、做了什么 | 已确认的事实，可以照写 |
| `inferred` | 气氛、动机、猜测 | 推断，顺着写就行，不要当成既定设定 |
| `uncertain` | 拿不准 | 不确定，写的时候模糊一点 |

**规则**：一个字段已经是 `confirmed` 时，只有同样是 `confirmed` 的改动才能覆盖它。
`inferred` 的改动会被挡下来，记进 `pending` 等人确认（`force` 参数给以后的人工确认留口子）。

真机跑批里这条规则真的挡下过一次：模型想把 `currentAction` 从「她合上书，侧过头质问玩家」
改成「她拎起书包带，准备和玩家一起去小卖部」——后者只是它的推断，挡下来是对的。

**但这条规则一开始写得太宽，把状态冻住了**：`currentAction` 被 confirmed 锁住之后，
后面每一轮都改不动它，「正在发生什么」停在了第三轮。所以规则收窄成
**只保护「像设定一样的东西」**——地点、时间、天气、在场的人、未收的线；
`currentAction` 和 `emotionalTone` 是瞬时字段，每轮都该更新。

## 4. 拼进提示词

回合层里的「当前场景」变成结构化的一段，每个字段带可信度：

```
本轮状态：
当前场景：
- 地点：午休的教室（已确认的事实，可以照写）
- 时间：午休（已确认的事实，可以照写）
- 在场：深月风花（推断，顺着写就行，不要当成既定设定）
- 正在发生：玩家问起放学后有没有事（已确认的事实，可以照写）
- 气氛：别扭里夹着一点在意（推断，顺着写就行，不要当成既定设定）
- 还没收的线：左手绷带的原因（推断，顺着写就行，不要当成既定设定）
- 角色卡设定里的场景（状态里还没记地点，以它为准）：午休的教室。窗开着。
- 未完成的剧情线：…
- 篇幅提示：只在玩家明确要求展开、续写或简短回答时提供；普通回合不设固定字数。
```

两个细节：

- **状态里没有地点时补一句角色卡的场景。** 状态只记变化，地点没变就不会出现在状态里；
  不补这一句，模型会以为「现在在哪儿」没有交代。
- **剧情线合并两个来源**：场景状态里的 `unresolvedThreads`（导演每轮更新的「此刻还没收的线」）
  排前面，关键事实里的 `flags`（长线事件）排后面，去重后最多五条。

状态在界面上只读展示：顶栏大脑图标打开的面板顶部会列出当前场景状态，
每一条都带可信度说明。玩家不用猜模型现在以为自己在哪儿。

## 5. 真机验证（2026-10-18）

`pnpm state-check`：一张卡、连续 6 轮，每轮都走真实的导演阶段。
模型 `yosei-router / deepseek-v4-flash-200k`。

| 指标 | 结果 |
| --- | --- |
| 总变化 | 16 处 |
| 被挡下 | 0 处 |
| 可信度分布 | confirmed 8 · inferred 8 · uncertain 0 |
| 没有状态变化的轮次 | 0 |

最终状态：

```
- 地点：午休的教室（已确认的事实，可以照写）
- 时间：午休（已确认的事实，可以照写）
- 在场：深月风花（推断，顺着写就行，不要当成既定设定）
- 正在发生：玩家问起放学后有没有事，深月风花回答了没有，又反问回去。（已确认的事实，可以照写）
- 气氛：别扭里夹着一点在意（推断，顺着写就行，不要当成既定设定）
- 还没收的线：左手绷带的原因（推断，顺着写就行，不要当成既定设定）
```

### 调参过程中抓到的三个问题

1. **地点和时间一开始根本没人写。** 提示里说「只写变化的字段」，导演就理解成
   「地点没变就不用写」，结果这两个字段一直空着。补了一条：状态里还没有地点或时间时，
   这一轮要按角色卡的场景或正文补上。
2. **可信度一个都没标。** 提示里说了要标 `status`，但 JSON 骨架里没有它，模型就照骨架输出。
   把 `status` 写进骨架之后，8 处 confirmed / 8 处 inferred 分得清清楚楚。
3. **瞬时字段被锁死。** 见 5.3 那一节：覆盖保护收窄到「像设定一样的东西」。

三条都不是靠读代码发现的，是靠 `state-check` 连着跑几轮看出来的。

## 6. 验收对照

| Phase 5 要求 | 落地位置 |
| --- | --- |
| 5.1 场景状态模型 | `lib/scene/types.ts` 的 `SceneState`，字段与建议一致，另加 `status` / `updatedTurn` / `pending` |
| 5.2 不要每轮让主模型重写全部状态 | 状态由导演阶段顺带输出（`statePatch`），不额外调模型 |
| 5.2 只保存变化项 | `applyScenePatch` 只把值变了的字段记进 `changes`，也不刷新未变字段的轮次 |
| 5.2 导演顺便输出状态变化 | `DIRECTOR_SYSTEM_PROMPT` + `DIRECTOR_STATE_HINT`；服务端路径随 `meta` 帧回传 |
| 5.3 区分 confirmed / inferred / uncertain | `StateFactStatus`，逐字段标注；提示词里给每种状态一句说法 |
| 5.3 猜测不能永久写成设定 | confirmed 字段挡得住非 confirmed 的覆盖，被挡的进 `pending`；`force` 留给以后的人工确认 |

## 7. 已知取舍

- **状态由导演给，不是独立的轻量模型调用。** 省一次调用，代价是导演的 JSON 一旦坏掉，
  这一轮既没有节拍也没有状态变化（正文照常生成，只是状态不更新）。以后要更准，
  可以换成独立的轻量调用，`sanitizePatch` 那层不用改。
- **覆盖保护只对「像设定一样的东西」生效。** 瞬时字段不受保护是有意的，
  否则状态会冻在某一轮。这条界线写在 `state.ts` 的 `TRANSIENT_FIELDS` 里。
- **`pending` 只记录、不消费。** 被挡下来的改动留在状态里等人确认，
  界面暂时不展示。这就是 5.2 里「以后再加入人工确认」的接口。
- **状态每轮占一点预算。** 六个字段加可信度说明大约 150 字，比角色卡里那句场景略长，
  换来的是「第 30 轮还知道在哪儿」。
- **状态不进前缀，也不进导出。** 它是给模型看的此刻，不是作品的一部分；
  EPUB 导出走的是消息正文和章节结构。
