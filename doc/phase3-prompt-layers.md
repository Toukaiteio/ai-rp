# Phase 3：强化提示词组装

前两个阶段解决「坏回复怎么办」。Phase 3 解决「好回复怎么更容易被写出来」：
把提示词分成稳定层和回合层，把最容易漂移的要求放到离生成最近的位置。

- 代码入口：`lib/prompt/index.ts`（组装）、`lib/prompt/system.ts`（回合层文案）、`lib/prompt/mode.ts`（回合模式）
- 测试：`lib/prompt/assemble.test.ts`、`lib/prompt/mode.test.ts`、`lib/prompt/turn-plan.test.ts`
- 真机结果：`doc/phase3-prompt-baseline.json`

---

## 1. 稳定提示层

**字节级稳定**，缓存断点打在它的最后一条上。只要角色卡和世界书不变，
这一段的字节就不变，各家的前缀缓存都能命中。

| 顺序 | 内容 |
| --- | --- |
| 1 | 讲述者身份与核心规则（`BASE_RULES`） |
| 2 | 消息块协议（`OUTPUT_CONTRACT`） |
| 3 | 角色卡自己的 `system_prompt` |
| 4 | 常驻世界书（`before_char`） |
| 5 | 角色卡：角色名 / 设定 / 性格 + 对话示例 + 玩家设定 |
| 6 | 常驻世界书（`after_char`） |
| 7 | 场景（角色卡的 `scenario`） |
| 8 | 常驻世界书（`before_scene` / `after_scene`） |
| 9 | 固定文风包 |
| 10 | 关键事实 |
| 11 | 滚动摘要 |

这一层里没有时间戳、随机数、请求 ID，也没有任何随轮次变化的东西——
**包括作者注**。作者注以前挂在 `after_scenario` 上，它每轮都可能变，
放在前缀里既打掉缓存，又会被后面的历史冲淡，所以 Phase 3 把它整体移到了回合层。

## 2. 回合提示层

放在**聊天历史之后**，一条 system 消息，顺序固定：

```
对白语言锁定（玩家最近一条输入的语言）
本轮状态
  - 当前场景：…
  - 未完成的剧情线：…；…
  - 本轮目标篇幅：150 到 300 字，最多不超过 700 字
本轮模式（…）：…
这一轮请按下面的要求写：      ← act 约束 + 正向示例
```

> 作者注在 Phase 4 里从这一层挪进了历史（最后一条玩家输入之前），
> 因为它比回合层更靠近生成。见 [phase4-author-note.md](phase4-author-note.md)。

为什么整层放在历史之后：系统提示在最前面，隔了几十轮历史之后约束力会明显衰减，
而 act 的写法、篇幅、本轮节奏恰恰是最容易漂移的。放在历史之后，它离生成最近。

**act 约束在这里再出现一次**，不是把整份协议抄一遍（那会挤掉历史预算），
只重复最容易走形的两条：

- act 只写一个旁观者能直接看见的短动作、姿势或表情，最多 20 个汉字，不带逗号，
  不写心理、原因、结果和比喻。不确定就写 narr。
- dlg 只放角色说出口的原话，不带括号、星号和「她笑了笑」这类叙述。
- 不替玩家说话、做决定，也不写玩家的动作和心情。
- 用讲述者的口吻，不要用第一人称写角色。

### 当前场景与剧情线

- **当前场景**：默认取角色卡的 `scenario`；调用方传 `scene` 就用传的，
  给后面接「场景线」留好接口。
- **活跃剧情线**：从关键事实的 `flags` 里现算（`activeThreads`）。
  值为 `true` 或一句状态表示还在进行，值里出现「已完成 / 结束 / 解决」就不再列出。
  最多四条，每条 60 字以内。

用 `flags` 而不是新造一个剧情线结构，是因为记忆工具只分人物、地点、事件三类，
其中事件天然对应「发生过的一件事」；项目规定不要发明原设定里没有的东西，
所以这里复用已有的键值，而不是加一层新数据。

## 3. 用正向示例替代过度否定

`BLOCK_EXAMPLES` 是**唯一一份示例**，前面的输出契约、回合层、修复提示都引用它：

```
合法示例（照这个粒度写，不要照抄内容）：
<act who="角色名">她抬眼。</act>
<act who="角色名">她把杯子放下。</act>
<act who="角色名">她的手指停住。</act>
<narr>她看了一眼门口，没有马上接话。</narr>
<dlg who="角色名">你刚才说什么？</dlg>
<scene>天亮了。</scene>
```

三条原则：

1. **不堆错误示例。** 错误样例会被模型当成「可以这么写」的素材，还占 token。
   `assemble.test.ts` 直接断言回合层里不出现「反例」「错误示例」字样。
2. **只留一份。** 各写一份会慢慢长歪，模型也会看到两套说法。
3. **示例旁边写清用途**：「照这个粒度写，不要照抄内容」。

## 4. 当前回合模式

```ts
type ResponseMode = "normal" | "short" | "dialogue" | "scene" | "continue";
```

| 模式 | 什么时候用 | 给模型的要求 |
| --- | --- | --- |
| `normal` | 普通叙述 | 接住玩家这一句，给一两个看得见的反应，停在玩家还能接话的地方 |
| `short` | 玩家只说了一两个词 | 一个动作、一段对白就够，不主动引入新剧情、新人物或新场景 |
| `dialogue` | 玩家在提问 | 让角色多说两句，动作只留必要的点缀，环境描写压到最低 |
| `scene` | 玩家要求换场、跳时间 | 允许换场和交代时间流逝，旁白可以多一些，不要求角色长篇对话 |
| `continue` | 玩家说「继续」，或上一段被截断 | 只接着上一段往下写，不新增转折，不重新解释前文 |

判定分两步，纯函数、可复现：

1. `inferResponseMode` 只看玩家这一句，优先级 **续写 > 换场 > 提问 > 太短 > 正常**。
   「继续」两个字必须最先判，否则会被当成 short；「我什么也没说」里的「什么」
   不是提问，所以先抹掉「什么也/没什么」这类陈述说法。
2. 导演阶段看过完整聊天记录，它的 `mode` 更准，允许覆盖。回合层是按 mode 拼的，
   所以覆盖之后重新组装一次（纯函数，很便宜）。

模式**不进前缀**：同样一张卡、同样历史，只换模式时 `cacheKey` 不变
（`assemble.test.ts` 有断言）。

## 5. 真机对比（2026-10-18）

同一批 26 组用例、同一个模型 `yosei-router / deepseek-v4-flash-200k`，
提示词版本从 `aedd6cd6` 变成 `09226833`。

| 指标 | Phase 1 | Phase 3 | 变化 |
| --- | --- | --- | --- |
| 质量门 | 原样落地 23 · 降级 3 · 拒收 0 | **原样落地 26 · 降级 0 · 拒收 0** | 全部一次过 |
| 符合机器预期 | 24 / 26 | **26 / 26** | +2 |
| act | 28 个，坏 4（14.3%） | **32 个，坏 0** | act 全部合规 |
| 对白 | 31 段 | **50 段** | +61% |
| 平均篇幅 | 109 字 | **122 字** | 更接近 150 到 300 字的目标 |
| 替玩家 / 复读 / 语言切错 / 人物漂移 | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 | 持平 |

模式分布：`dialogue` 13 · `normal` 11 · `scene` 1 · `short` 1。

**最明显的是 act：从 4 个不合格降到 0 个。** 这正好验证了 3.2 的判断——
act 约束只写在最前面的 System 里时会被长历史冲淡，在回合层再讲一次就稳住了。
对白段数涨了 61%，因为 13 组用例被判成 `dialogue`，模型确实按模式多写了台词。

需要说明的是：这是单轮样本，26 组各跑一次。act 从 4 到 0 有随机性成分，
但「回合层里再讲一遍 act」这个机制本身是确定的。

## 6. 预算影响

实测：一张普通卡 + 30 条历史，回合层占 **375 token / 605 字符**，
整个后置段（含记忆目录）598 token，前缀 1494 token。

```
blocks: { prefix: 1494, history: 1120, post: 598 }
```

在 16k 上下文里，回合层大约是 2.3%。它换来的是 act 合格率和对白密度，
性价比是正的。`assemble` 的预算表里 `blocks.post` 会体现这部分，历史预算相应减少——
如果以后把上下文调到 8k 以下，要重新看一眼这里。

## 7. 验收对照

| Phase 3 要求 | 落地位置 |
| --- | --- |
| 3.1 稳定提示层不频繁变化 | `assemble` 前缀段固定顺序、字节级稳定；作者注等变量全部移出前缀；`assemble.test.ts` 断言同输入两次字节一致、改模式不改 cacheKey |
| 3.2 回合提示层放在历史之后 | 一条 system 消息，含语言锁定、当前场景、剧情线、回合模式、输出要求；顺序在测试里逐项断言。作者注在 Phase 4 挪进历史，位置更靠后 |
| act 约束在回合层再出现 | `TURN_RULES` 第一条；测试断言回合层含「act 只写一个旁观者能直接看见的短动作」 |
| 3.3 正向示例替代过度否定 | `BLOCK_EXAMPLES` 五条合法样例，全局唯一一份；测试断言不出现「反例」「错误示例」 |
| 3.4 当前回合模式 | `lib/prompt/mode.ts` 五个模式 + 指令表；推断纯函数；导演可覆盖；模式不进缓存指纹 |

## 8. 已知取舍

- **作者注不再支持 `position`。** Phase 4 把它统一挪进了历史（最后一条玩家输入之前），
  见 [phase4-author-note.md](phase4-author-note.md)。少一个配置项，
  换来的是「它一定离生成最近」这个保证。
- **剧情线复用 `flags`。** 好处是不新增数据结构、不违反「不发明设定」；
  代价是它依赖模型主动把事件的完成状态写成「已完成」这类词，不写就一直在列表里。
- **模式推断是启发式的。** 中文问句常常没有问号，`什么也` 这种陈述说法要单独排除；
  误判的代价只是节奏偏一点（多写两句对白），不会像质量门那样拒收整轮。
- **回合层不是越长越好。** 它每轮都占预算，所以只重复最容易走形的两条 act 规则，
  没有把整份输出契约抄第二遍。要加内容先看 `blocks.post` 涨了多少。
