# Phase 7：记忆系统优化

前六个阶段把「此刻」和「欠着什么」管住了。Phase 7 收拾剩下的那一半：
**什么值得记、记了之后怎么不被改坏。**

- 分层说明：`lib/memory/layers.ts`
- 写入规则与冲突处理：`lib/memory/rules.ts`
- 接在函数调用上的守门：`lib/memory/journal.ts` 的 `applyMemoryWrite`
- 测试：`lib/memory/rules.test.ts`（23 条）、`lib/memory/write-guard.test.ts`（6 条）

---

## 1. 记忆分层

五层各管一件事，生命周期和注入位置都不一样。`MEMORY_LAYERS` 是它们的说明书：

| 层 | 记什么 | 存在哪儿 | 注入在哪儿 | 怎么淘汰 |
| --- | --- | --- | --- | --- |
| 当前场景记忆 | 此刻在哪儿、什么时候、谁在场、正在发生什么 | 会话 `sceneState` | 回合层「当前场景」，带可信度 | 每轮只存变化项，被新值覆盖 |
| 角色记忆 | 人物关系、习惯、过去的事 | 本机目录 `characters` | 历史之后的记忆目录 | 同名再写是更新；确认过的不会被推断覆盖 |
| 世界记忆 | 地点、组织、规则、背景 | 本机目录 `places` + 角色卡世界书 | 世界书进前缀，目录进历史之后 | 世界书跟卡走；目录按上限淘汰 |
| 剧情记忆 | 悬念、伏笔、已解决的事件 | 会话 `storyThreads` + 目录 `events` | 回合层「还没交代完的几件事」，每轮最多三条 | 已解决的不再注入，也不能被重新打开 |
| 风格记忆 | 角色常用语、说话节奏、禁用表达 | 本机目录 `style` + 角色卡 | 历史之后的记忆目录 | 来自卡或玩家明确要求，几乎不变 |

这一层的价值不在新代码，而在**把已有的东西归位**：
以前「记忆」是一个笼统的目录，现在每类内容都有明确的归属、
明确的注入位置和明确的淘汰方式，加东西之前先看它属于哪一层。

## 2. 写入规则：不是提到就记

`decideWrite` 判断一条候选该不该写进长期记忆，五条理由满足任意一条即可：

| 理由 | 判定 |
| --- | --- |
| 玩家明确确认 | 玩家这一轮明确点头（「对」「就是这样」） |
| 同一事实多次出现 | 同一段对话里出现 ≥ 2 次（`REPEAT_THRESHOLD`） |
| 对后续剧情有明显影响 | 涉及重要度 4 以上的剧情线，或已知人物 |
| 来自角色卡或世界书 | 卡上写着的，天然可信 |
| 被工具调用明确写入 | 模型主动调 `remember_*` |

一条都不满足就不写。**宁可少记，也不要把模型随口一句推断变成以后每一轮都要背着的设定。**

## 3. 冲突处理：保留旧事实

新旧内容不一致时（`isConflict`）：

```
保留旧事实  →  标记冲突  →  等玩家确认
```

`applyWriteRules` 的返回里，冲突项**不会出现在 `written`**，
而是进 `conflicts`，带着旧值、新值、轮次和命中的理由。
回给模型的话也写得很明确：

```
「深月风花」已经有记录：她说是烫伤。
你这次想写的是：其实是刀伤。
两者不一致，已保留原来的记录，等玩家确认后再改。不要重复尝试覆盖它。
```

最后一句是有意的：不点明「旧的算数」，模型会换个说法再试一次，
一轮一轮地把同一条记忆反复顶。

**玩家确认是唯一的例外**：`confirmCandidate` 产出的候选带 `overwriteConfirmed`，
这时才允许覆盖。注意区分两件事——「玩家确认这件事存在」不等于
「玩家确认旧记录写错了」，所以只带 `playerConfirmed` 仍然会被挡下来，
必须是对那条**改动**的确认。

## 4. 接在真实链路上

规则只有接上工具调用才算数。`applyMemoryWrite` 是 `applyChatTool` 的守门版：

```
模型调用 remember_character
  ↓
先查同名条目有没有记录
  ↓ 内容不同
保留旧记录 + 返回冲突提示（journal 一个字都没改）
```

ChatScreen 的续写轮现在走 `applyMemoryWrite`，
被挡下的冲突记进 `memoryConflictsRef`，开发模式下打一行日志。

`write-guard.test.ts` 直接验证这条链路：同名改内容之后，
`journal.characters["深月风花"].detail` 仍然是旧值，而且返回给模型的话里带着
「保留原来的记录」。

## 5. 验收对照

| Phase 7 要求 | 落地位置 |
| --- | --- |
| 7.1 记忆分层（场景 / 角色 / 世界 / 剧情 / 风格） | `MEMORY_LAYERS` 五层，每层写明记什么、存哪儿、注入在哪儿、怎么淘汰；测试断言五层齐全 |
| 7.2 不是每个提到的事实都自动记忆 | `decideWrite` 五条理由；一条不满足就不写 |
| 7.2 至少满足一项才写入 | 同上，`applyWriteRules` 把不满足的记进 `skipped` |
| 7.3 冲突时保留旧事实 | `applyWriteRules` 的冲突项不进 `written`；`write-guard.test.ts` 断言 journal 未被改动 |
| 7.3 标记冲突 | `MemoryConflict`（层、键、旧值、新值、轮次、理由），进 `conflicts` 并打日志 |
| 7.3 等玩家确认 | `confirmCandidate` + `overwriteConfirmed`；只有对改动的确认才放行 |
| 7.3 不让最新输出直接覆盖长期记忆 | `applyMemoryWrite` 接在工具调用上，同名改内容一律先挡 |

## 6. 已知取舍

- **自动判定只做了「工具调用」这一条。** 另外四条理由的判定函数都写好了、
  也测过了，但目前只有函数调用这条真正接在链路上。
  自动从正文里抽取事实并判定「玩家确认 / 多次出现」需要额外的抽取步骤，
  那是下一步的事；现在这样至少保证**没有任何自动写入能绕过规则**。
- **冲突只记录，还没有确认界面。** 玩家看不到「模型想改这条记忆」的提示，
  只能等下一步把 `conflicts` 接到界面上。现在它至少不会静默改坏数据。
- **风格层还是空的。** `style` 这一类在分层里占位，实际内容目前靠角色卡
  （`personality`、`mes_example`、`author_note`）承载。等有了「角色常用语」
  的自动提取再往里写。
- **五条理由没有权重差别。** 只要满足一条就写，不区分「玩家确认」和
  「来自角色卡」谁更可信。冲突处理会兜住大部分风险。
